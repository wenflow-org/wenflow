# Anderson Annotation Iteration Direction in Path Scenario

## Background

Current Anderson-related logic in the path scenario has been adjusted from blocking post-processing to execution during the enrichment phase after paths become available.

In the path scenario, two semantic layers need to be distinguished:

1. **Path本体** (Path Entity): Stage division, stage goals, task sequence, and task content.
2. **Anderson标注** (Anderson Annotation): Educational definition for each task, explaining "what is being learned, to what depth".

## Current Layering

### Phase One

Phase one is the educational definition layer, primarily outputting:

- Task knowledge type preference
- Task target cognitive level
- Task learning objectives
- Core concepts
- Transferability
- Annotation confidence

This layer is not the main content for users, but structured definitions for system and subsequent teaching scenarios.

### Phase Two

Phase two is the display translation layer, core role is converting phase one educational judgments into shorter labels easier for users to understand.

For example:

- Understanding method principles
- Hands-on practice
- Designing new methods

## Assessment of Current Path Scenario

### Is Phase One Input Sufficient

Current phase one batch annotation input includes:

- Overall learning goal
- User background summary
- Domain/subject
- All task list
- Each task title
- Each task description
- Task type
- Stage goal belonging
- Target type analysis suggested distribution

**Conclusion**: Sufficient, but not particularly rich. Can support current educational definition tasks, but for future accuracy improvement, stronger local context can be added.

### Should Phase Two Exist Independently

In path scenario, phase two currently only translates phase one results into short labels, and such translation already has stable mapping tables.

**Conclusion**:

- In path scenario, phase two need not continue per-task separate calls
- More reasonable approach:
  - Short term: Directly use local mapping table to generate display labels
  - Medium term: If scene-specific labels needed, consider generating display labels in one batch annotation call

## Recommended Iteration Direction

### Path Scenario Short-term Solution

- Keep phase one batch annotation
- Cancel phase two per-task separate generation
- Display labels generated by platform based on phase one results via local mapping

### Path Scenario Medium-term Solution

- Merge phase one and phase two
- Batch Anderson annotation outputs both:
  - Educational structured definition
  - User-readable labels

## Insights for Future Teaching Scenarios

- Teaching scenarios should truly rely on phase one educational definitions
- Phase two labels are more suitable for user understanding and frontend display layer
- If teaching scenarios later need labels, should also prioritize producing with phase one batch, avoiding per-task secondary generation
